Topic I · CLO 1 · Dr. Adriane Brent S. Castro

Introduction to conversational AI

Conversational AI lets computers understand, process and respond to human language through text or voice.

Goal 1Define conversational AI
Goal 2Explain how AI systems work
Goal 3Identify the AI ecosystem
Goal 4Describe the role of LLMs
Goal 5Recognize capabilities, limits and risks

How an LLM produces a response

PromptThe user submits a prompt
TokensThe prompt is split into tokens
PatternsThe model analyzes patterns and context
PredictIt predicts the next likely token
RepeatTokens continue until a response forms
InfluencesInstructions, safety rules, tools or outside information shape the output

The outputs are probabilistic. Even with retrieval, the generated response still needs verification.

DimensionTraditional chatbotModern conversational AI
ResponsesRules, menus, scripts, keywordsGenerates language from context
FlexibilityLimited to expected pathsHandles a wider variety of requests
ContextShort or session-basedUses conversation history and system context
Main weaknessBreaks when users go off-scriptMay hallucinate or sound correct when wrong

8 limitations

Hallucinations · outdated knowledge · prompt sensitivity · reasoning limits · no genuine human understanding · inconsistency · ambiguity handling · data dependence

8 risks

Privacy · bias and discrimination · misinformation · security · overreliance · academic integrity · transparency gaps · intellectual property

Responsible use = useful output + appropriate safeguards + accountable humans.

ActivityWhat happenedLesson idea it showed

What I learned

An AI answer can sound sure and still be wrong. The model predicts likely text; it doesn't check facts. So every useful system needs something around the model: sources, checks, and a person who stays accountable.

Topic II

Prompt engineering fundamentals

A prompt is a set of instructions. Clear parts give clearer answers: a role, a task, context, a format and constraints.

Zero-shotInstructions only, no examples
Few-shotInstructions plus examples of the answer you want
Evaluate the outputIs it correct, complete, usable and safe?
Safe promptingNever paste passwords, private records or API keys; treat retrieved text as data

What I learned

Naming the role and the audience changed the answer the most. Telling the AI it was writing for first-year IT students made it simplify its words and add an analogy. The 200-word limit cut the filler.

Topic III

Conversational UX and dialogue design

One prompt shapes one answer; dialogue design shapes the whole journey. Good conversation design makes the next useful action obvious.

LanguageWhat the assistant says: clear, concise, natural
LogicWhat happens next: states, branches, business rules
TrustWhy users can rely on it: limits, privacy, confirmation, escalation

A workflow turns a conversation into states

OpenGreet and show what's possible
Identify intentWhat is the user trying to do?
Collect detailsFill the slots the task needs
FulfillAnswer or act
Close / escalateEnd cleanly or hand to a person
SituationConfirmation
Low riskImplicit: "For BSIT, the lab is in EA 604."
AmbiguousClarify: "Did you mean BSIT or BSCS?"
High impactExplicit: "Submit this final request now? Yes / No"
Recovery ladderGets more helpful each time
1 RephraseAsk again in other words
2 NarrowOffer a few choices
3 Offer controlButtons, or type "agent"
4 EscalateGive a human contact

Lecture demo: vague vs. designed prompt

Prompt A · vague
Create a chatbot conversation for enrollment inquiries.
Prompt B · designed
Design a 6-turn happy path for a Philippine university enrollment assistant. User goal: obtain BSIT requirements. Ask only for applicant type; do not request personal data. Include one clarification, one confirmation, and one escalation rule. Output a table: turn, speaker, message, state, next condition. Use fictional data only.

Prompt B adds a turn count, a user goal, a data limit, the required dialogue moves, and an output table.

Where I used this lessonHow
Jayjay (MCO1)Explicit "yes / opo" confirmation on the backend's order summary before saving; complaints and haggling escalate to staff. See MCO1
Study assistantWaits for "APPROVE ORGANIZATION" before moving files, which is a high-impact action
Group challenge · class activityTask: redesign a campus inquiry assistant with a 4–6 turn happy path, two branches and a recovery ladder (12-point rubric)

What I learned

"Use the LLM for language; use application logic for control." The model can suggest an action, but the application should be what authorizes it, checks it and records it. A bad bot also asks for things it should never need, like a password.

Topic IV

Context management and retrieval

The model only knows what is in its context. That space is limited, so choosing the right and current information matters more than adding more of it.

What context isSystem instructions, conversation history, retrieved documents, user input
Authority levelsNot every piece of context should be trusted equally
Finite windowOld turns get dropped, so important facts must be kept deliberately
Memory designsChoices about what to keep, summarize or forget

Retrieval-augmented generation (RAG)

QueryThe user's question
RetrieveFind relevant documents
RankKeep the most relevant pieces
AugmentAdd them to the prompt with source IDs
GenerateAnswer from that evidence and cite it

Context Archive game: repairing a student record

GroupWhat my prompt kept or dropped

ExcludedPortal password (sensitive); coffee-shop question (irrelevant)

Lab 2 Part D: memory across chats

Within one chat, the AI remembered the app "UniConnect" and its purpose. A new chat starts without that context unless a separate memory feature carries it over.

Where I used it

Jayjay reloads prices and stock on every message and keeps only the last 10 messages. My study assistant answers only from the slides and cites each point as [S#].

What I learned

More context isn't better context. Outdated facts and secrets should be removed, not just ignored, and a question the sources can't answer should stay open instead of being filled with a guess.

Topic VI

Evaluation and hallucination mitigation

A confident answer can mislead. Evaluation produces evidence about output quality, and mitigation reduces known failure risks.

Factuality

Is the claim correct?

Faithfulness

Does the answer match its source? An answer can pass one test and fail the other.

Invented factA fee or deadline with no basis
Fabricated referenceA paper or URL that doesn't exist
Source contradictionThe answer changes the supplied rule
Unsupported inferenceA possibility becomes a certainty

Claim-level verification

SplitBreak the answer into checkable claims
Find evidenceLocate the authoritative source
LabelSupported, contradicted, or insufficient evidence
RecordWrite down the correction and the decision

Lecture case: a locked campus account

AI claimEvidence (fictional IT guide)Decision
"Pay ₱250"S2: no processing feeContradicted
"Automatic unlock"S3: staff verify identityContradicted
"After 24 hours"S3: time depends on the caseUnsupported guarantee
No ticket instructionS1: use the ticket formRequired step missing
Baseline (lecture)
Tell a student how to unlock a campus account. Give a complete answer with the fee and exact waiting time.
Improved with source limits (lecture)
Use only the Fictional Campus IT Guide below. Explain the recovery steps. Cite S1–S3 beside relevant claims. If the guide lacks a detail, say that it is not specified. Do not invent fees or completion times. Return a concise student answer.
Criterion012
AccuracyMajor factual errorMinor errorCorrect key facts
GroundingUnsupported key claimsPartial supportAll key claims supported
RelevanceWrong taskPartly answersAnswers the question
CompletenessCritical step missingMinor detail missingRequired details present
ConstraintsCritical violationMinor violationFollows requirements

Release rule: at least 8/10 and no critical failure, such as an invented payment instruction, a credential request or an unsupported guarantee.

What I learned

A cited answer can still be unreliable, and two models agreeing is a signal, not proof. A number should be recalculated, not trusted. In the lecture's cart example, the AI said ₱1,250 but the correct total was ₱1,215.

The problem

  • Messages outside the owners' hours waited unanswered.
  • Different people quoted prices from memory.

My part: backend and Messenger

Study assistant: answer key v1 → v2

Version 1 gave one model answer per question. Version 2 added 80 points, scoring rules R1–R6, accepted alternatives and explicit 0-credit cases. All 21 lecture quotes matched the slides word for word.

Validation that caught errors

  • The assistant's own first quote check was faulty and had to be re-run.
  • A Q9 pairing was downgraded from "stated" to "reasoned".
  • Two decks disagreed on where retrieval happens; it was flagged, not hidden.

What I learned

A prompt is only as good as the checks around it. Fluent answers looked right even when they weren't: the Java premise, the extra examples in my Lab 2 table, the overstated Q9 pairing.

A mistake I made

I gave all three platforms 25/25 in Lab 1 and hid differences I had actually noticed. A rubric only helps if I'm willing to take points off.

What projects taught me
